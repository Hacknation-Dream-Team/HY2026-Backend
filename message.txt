# Schemat bazy 

Baza: PostgreSQL + PostGIS (Neon). Pełny SQL w `schema.sql`, diagram w `erd-draft.md`.

Połączenie: zmienna środowiskowa `DATABASE_URL` (connection string dostajesz prywatnie, nie commituj go do repo).

## Pliki

| plik          | co robi |
|---------------|---------|
| `schema.sql`  | **kasuje wszystkie tabele i dane**, potem tworzy schemat od nowa |
| `seed.sql`    | słownik aut z EEA (1430 wierszy) + dane mockowe (Warszawa, 3 firmy, 60 userów). Odpalać po `schema.sql`. Hasło wszystkich mockowych kont: `haslo123` |
| `queries.sql` | zapytania podglądowe (trasy, ogłoszenia, matche, GeoJSON na mapę) |
| `scripts/load_eea_raw.py` + `.github/workflows/refresh-car-models.yml` | odświeżenie `car_models` z EEA (patrz niżej) |

## Model w skrócie

- **Organizacja:** każdy user należy do dokładnie jednej firmy. Matching tylko w obrębie tej samej firmy.
- **Kierowca:** `routes` (trasa) → `route_points` (przystanki po kolei) → `advertisements` (oferta: kiedy, ile miejsc, którym autem). Jedna trasa może mieć kilka ogłoszeń (np. pn–pt 7:30 i sobota 10:00).
- **Pasażer:** `ride_requests` (skąd → dokąd, kiedy).
- **`matches`:** jeden wiersz = jeden pasażer na jednym ogłoszeniu, z przystankiem wsiadania i wysiadania. To umowa, przy commute trwa tygodniami.
- **`rides`:** dziennik: pasażer z danego matcha faktycznie pojechał danego dnia. Brak wiersza = nie jechał.

```
organizations 1 ── N users
users 1 ── N users_cars N ── 1 car_models
users 1 ── N routes 1 ── N route_points
                  routes 1 ── N advertisements N ── 1 users_cars
users 1 ── N ride_requests
advertisements 1 ── N matches N ── 1 ride_requests
matches 1 ── N rides
```

## Typy

| typ            | wartości |
|----------------|----------|
| `weekday`      | `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun` |
| `match_status` | `pending` (pasażer się zgłosił), `accepted` (obie strony się zgodziły), `rejected` (kierowca odmówił), `cancelled` (ktoś zrezygnował później) |
| `user_gender`  | `female`, `male`, `other` |

## C# / Npgsql

Enumy i PostGIS trzeba zarejestrować, inaczej odczyt się wywali:

```csharp
public enum Weekday { Mon, Tue, Wed, Thu, Fri, Sat, Sun }
public enum MatchStatus { Pending, Accepted, Rejected, Cancelled }
public enum UserGender { Female, Male, Other }

// EF Core (Npgsql 9+):
options.UseNpgsql(connStr, o =>
{
    o.UseNetTopologySuite();
    o.MapEnum<Weekday>("weekday");
    o.MapEnum<MatchStatus>("match_status");
    o.MapEnum<UserGender>("user_gender");
});
```

- Npgsql domyślnie zamienia `Mon` → `mon`, `Pending` → `pending`, więc nazwy się zgadzają bez dodatkowej konfiguracji.
- `weekday[]` → `Weekday[]` (albo `List<Weekday>`).
- `geography(Point, 4326)` → `NetTopologySuite.Geometries.Point`. Uwaga na kolejność: `X` = długość (lng), `Y` = szerokość (lat), SRID 4326.
- `time` → `TimeOnly`, `date` → `DateOnly`.

## Matching: `find_matches`

Gotowa funkcja w bazie: dla zapytania pasażera zwraca pasujące ogłoszenia, najlepsze pierwsze (najbliższy przystanek, potem najmniejsza różnica godzin).

```sql
SELECT * FROM find_matches(5);                          -- domyślnie: 500 m, ±15 min
SELECT * FROM find_matches(5, 800, '30 minutes');      -- luźniejsze kryteria
```

Warunki: ogłoszenie aktywne, ta sama firma, kierowca ≠ pasażer, co najmniej jeden wspólny dzień, `departure_time` w oknie czasowym, przystanek w promieniu od startu pasażera i dalszy przystanek w promieniu od jego mety, wolne miejsce, brak istniejącego matcha tej pary.

Zwraca: `advertisement_id`, `driver_id`, `pickup_seq`, `dropoff_seq`, `pickup_distance_m`, `dropoff_distance_m`, `departure_time`, `free_seats`. Z tych pól backend tworzy wiersz w `matches` (status `pending`).

Ograniczenia: okno czasowe porównuje godzinę wyjazdu kierowcy z godziną pasażera (bez szacowania czasu dojazdu do przystanku); nie obsługuje przejścia przez północ.

## Odświeżanie `car_models` z EEA

Backendu nie dotyczy, opis dla porządku. Raz na jakiś czas (gdy EEA opublikuje nowy rok) ręcznie odpala się workflow `refresh-car-models` w GitHub Actions:

1. `scripts/load_eea_raw.py` pobiera surowe agregaty z EEA do CSV,
2. CSV trafia do tabeli `eea_raw`,
3. `CALL refresh_car_models();` czyści nazwy marek i modeli, liczy spalanie i robi upsert do `car_models` po `(brand, model, fuel_type)`. Istniejące `id` zostają, więc `users_cars.brand_id` się nie rozjeżdża.

`eea_raw` to tabela robocza (staging), aplikacja jej nie używa. Funkcje `eea_starts_with_word` i `eea_clean_model` to pomocnicze funkcje procedury. Czas odświeżenia: ok. 5 s.

## Czego baza NIE pilnuje (musi backend)

- `pickup_seq` / `dropoff_seq` muszą istnieć w `route_points` trasy tego ogłoszenia (nie da się tego zrobić FK).
- Zaakceptowanych matchy na ogłoszeniu nie więcej niż `advertisements.seats`.
- `advertisements.users_car_id` musi należeć do kierowcy trasy (`users_cars.u_id = routes.user_id`).
- Kierowca i pasażer z tej samej organizacji; kierowca ≠ pasażer.
- Wpis w `rides` tylko dla matcha `accepted` i tylko w dzień, który jest w `days_of_week` ogłoszenia i zapytania.
